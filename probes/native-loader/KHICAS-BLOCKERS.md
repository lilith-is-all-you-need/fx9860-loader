# KhiCAS Loader 卡点与下一条验证路线（2026-11-15）

当前结论（2026-11-16 更新）：**大镜像存储直映与 OS 补页已在 Probe3 实机闭环通过，
完整 KhiCAS Loader 尚未打通。** 正式接入仍需解决驻留 RAM 与 KhiCAS 私有内存池冲突、
三个影子页及真实程序初始化/回调交接。已发布 Loader 的 160 KiB 拒绝保护保持不变。

## 已发布 Loader 实际停在哪里

本次样本为 2,094,444 字节，SHA-256
`4a9d1c18009d987dc7c8745b7fc099b3c6e8006ebbb2ee5e4b483934be757473`。
当前 Loader 在验证 profile 后发现大于 160 KiB，显示 `Need file mapping`，
在目标初始化之前拒绝；没有执行到 KhiCAS main。

目前实现把整个 BIN 复制进 RAM，按原来 `0x00300000` 起的地址装入映射，
从 `0x00300200` 进入完整 CRT。这个方式使代码、常量池和资源之间的地址关系不变，
也让原文件只改后缀即可，但不适合约 2 MiB 镜像。

把 160 KiB 限制调大没有解决方案意义：分配器后面仍要拿到整份镜像的 RAM。
模型的默认 192 KiB 堆是声明的诊断配置，并不是已测出的实机可用预算。
KhiCAS 又使用独立的物理 RAM 区域；现 profile 禁止占用 `0x88051000..0x8807D000`。
Loader 自身、栈、补丁页及 KhiCAS 的分配器还必须各自有实际内存预算。

## 64 项 TLB 不是地址空间上限

此文件需 512 个 4 KiB 页。当前 Loader 的策略是把目标页固定保留在 UTLB，
并为 OS 留槽，因此无法用这一策略常驻全部页。
但 **64 项 TLB 不等于最多只能运行 256 KiB 程序**：TLB 是翻译缓存，正常 OS
可以在缺页/缺项时从持久映射关系重新填入。

原来缺少 `.bin` 文件到存储后端的完整映射，以及条目被替换后仍能恢复的机制。
这两项如今已有 Probe3 的实机证据，尚需集成进正式 Loader。
若只让入口几页可执行，之后调用远处函数、读取字符串/符号表/图片、返回旧代码页时
仍会失败。成功进入 main、显示首页或做一次计算都不足以证明它稳定。

## 本轮发现的有利条件

现 profile 对 51 个 `0x80010070` 常量池做经指令形式确认的替换。
按原文件偏移除以 4096，这些修改仅落在页号 **0、470、471**，即文件区间：

| 页号 | 文件偏移区间（左闭右开） | 原虚拟地址区间 |
| --- | --- | --- |
| 0 | `0x000000..0x001000` | `0x00300000..0x00301000` |
| 470 | `0x1D6000..0x1D7000` | `0x004D6000..0x004D7000` |
| 471 | `0x1D7000..0x1D8000` | `0x004D7000..0x004D8000` |

因此只针对**当前已识别的 gateway 补丁**，可修改影子页预算为 **12 KiB**，
不必把约 2 MiB 全部复制进 RAM。这是值得继续验证文件映射方案的具体依据。
它不证明其他初始化、自修改代码、退出适配或运行期写入绝不会要求更多页面。

## 我建议的实现顺序

若能取得与实机一致的 GIII OS 映像（当前探测版本为 `03.70.0200`），优先分析
add-in 启动、文件分片查找、TLB miss 补充以及切换/退出清理路径，再做下面的定向验证。
OS 映像可提供实际代码与静态表，但不包含当前 RAM 中的活动映射、分配和回调状态，
不能仅凭反汇编宣称跨文件碎片、TLB 淘汰和菜单切换已验证。
暂不优先实现通过 Bfile 在异常处理内搬入页面的通用 RAM 换页器。
页边界由页大小/对齐决定，可枚举测试；核心未知是映射所有权和异常/OS 重入约束，
不是要求应用每次访问都寻找新的 RAM 空隙。

1. **优先验证存储直接映射。** 在 GIII/对应 OS 版本上确认如何取得一个已打开
   `.bin` 的实际文件分片及生命周期，读取首、中、尾和跨分片数据与 Bfile 输出核对。
   文件重写、移动、重启后重新取得映射；不要把旧物理地址永久写死在 PC 生成的 profile。
2. **原文件映射 + 三个 RAM 影子页。** 原地址空间保持不变，只把需修改的页重定向到
   RAM。验证 OS 调用、TLB 淘汰、菜单恢复后映射仍然成立。大页可减少 TLB 压力，
   但前提是文件物理分片连续且满足对齐，不能把碎片化文件假设成连续 ROM。
3. **如果不能复用 OS 的映射服务，再研究自建分页器。** profile 可以提供页表规则、
   补丁、保留区和已确认适配；Loader 必须另有可靠的异常处理/补页路径。
   缺页时调用 Bfile 可能重入 OS，尤其原来就在 syscall、定时器或退出回调中时；
   页替换还要同步指令缓存、避免覆盖当前栈和回调代码。这条路线成本明显更高。
4. **映射通过后再验收 KhiCAS 功能和生命周期。** 覆盖初始化、复杂计算、跨页资源访问、
   文件读写、MENU 切换、退出和再次启动；任一缺失调用仍单独记录。

这与“一份 BIN 配一份 profile”的架构相容，但 profile 应区分：
编译期可固定的文件哈希/补丁/虚拟布局，以及运行时必须重新取得的物理分片/分配结果。
目前建议继续保留完整镜像和 CRT，不删除开头字节，也不把所有 CRT 工作先假定已被 Loader 替代。

## 映射之后还有什么风险

这份 KhiCAS 的已识别 syscall stub 共涉及 73 个不同编号。
新增模拟器入口后仍有九个编号没有处理器：
`0x0026,0x0218,0x0268,0x0374,0x04B0,0x04D1,0x04DD,0x0924,0x0EA1`。
这是**静态存在的调用入口清单**，不是已经证明本轮测试执行到的九个故障。
0x01E7 已有部分实现，脏容器提交仍未支持。
其中有显示、设置、主存储等接口，也有仍缺少可靠定义的入口。
光标闪烁、键盘重复、copy-back 数据缓存、所有外设时序也未完整模拟。

所以“补 syscall”能提高后续软件兼容性，但不能自动给 Loader 增加可用 RAM，
也不能让实机 OS 知道一个任意 `.bin` 的原地址映射。
反过来，文件映射成功也不自动证明全部 KhiCAS 功能已兼容。

## 本轮实测与证据边界

相同原文件在模拟器的 KhiCAS 专用诊断内存布局下直接启动，可进入计算界面，输入 `2+2`
得到 `4`。经 Loader 则仍由大小检查拒绝。这两条结果没有互相替代。
专用布局避免已知 RAM 冲突，不是经过完整实机验证的 OS RAM 分配图。

Wolf 的原镜像在 `00309F68` 附近读出 `A0000000` 并跳转，用户本轮补充实机观察为 OS 重启。
新模拟器对这条路径保存报告后重建 HLE OS，直接启动和 Loader 启动都得到相同行为。
这支持“退出进入重启路径”，但没有据此宣称其后所有固件行为都正常且非崩溃。
11 月 15 日 Fruit 在未知 `0x01E7` 留档重启；11 月 16 日已补充其空闲清理语义，
重测继续在未实现的 `0x0218` 留档重启，尚未通过完整退出。Minesweeper 正常保存、菜单
替换清理及重入仍通过。

文件分片与 FX/CG 差异的原始研究参考：
[Casiopeia file mapping discussion](https://www.casiopeia.net/forum/viewtopic.php?f=11&t=1742)。
其中 CG 的块地址接口不能未经验证直接挪用到 FX/GIII；本方案中的影子页和验证顺序
是依据本地镜像/profile 所作的工程推导，不是该资料已经证明可用的现成实现。

## 2026-11-16：文件映射探测进展

3.40/3.60/3.71 的九个升级固件分支确认了 RAM 页表和补页核心，已加入可选固件辅助 HLE。
[Probe3](../file-map-probe/README.md) 使用与此 KhiCAS 等长的自制 BIN，在 48 KiB 堆预算内
完成 512 页映射执行、文件操作恢复、RAM 影子页和退出回调的模拟验证。
随后收到 03.70.0200 实机报告：512 页逐页校验、两轮执行及文件操作后的第三轮执行、
RAM 影子页、定时回调、MENU 替换退出及重入全部通过。细节见 Probe3 文档和硬件结果 JSON。
实机地址刷新三次分别发现 6、3、11 页发生变化，正式 Loader 不能把物理页表永久写入 PC profile。

实测还明确了下一个内存冲突：探测器常驻代码在 880535C0..88055BF4，影子页在
88056000..88057000，均与 KhiCAS 的保留区 88051000..8807D000 重叠；上下文也部分重叠。
这不是本次 Probe 的失败，因为测试 BIN 不使用 KhiCAS 的私有池；但不能照搬该内存布局启动 KhiCAS。
可继续评估压缩/搬移 Loader 常驻数据，或通过 profile 精确适配 KhiCAS 的私有池边界，
必须核对全部相关引用及分配所有权，不能只挑一块看似空闲的 RAM。

没有据此修改已发布 Loader 的大文件拒绝保护。完整 KhiCAS 经新映射方式启动仍待上述集成，
不能将 Probe 通过等同于它已经跑通；单次实机运行也不能证明长期或所有存储布局的稳定性。
