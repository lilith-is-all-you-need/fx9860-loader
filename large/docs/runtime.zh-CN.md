# 动态超限加载与源码库

`ExtLoad.g1a` 现在从 `/FXAPPS/<ID>/EXT.PRF` 读取镜像大小、有效页数、页表容量和
完整 SHA-256，然后启动同目录 `IMAGE.BIN`。同一个加载器可处理不同大小、已经接入
运行时协议的镜像，不再按 699 页重新编译。目录 ID 为 1–8 个英文字母、数字或下划线；
电脑端以名称加短 hash 生成。支持 `APP.MET` 中的英文标题，最多显示 16 个项目；启动前
关闭所有搜索句柄。没有目录项目时仍支持根目录 `EXT.PRF` 加 `KHICAS.BIN`。

默认页表容量向上取整到 16 页，例如 699 个有效页对应 704 项；也可在 profile 指定
更大的容量，最多 768。余量只占页表 RAM，未用项清零，不会变成有效程序页面。
实际 TLB 使用 0–54 中可用的槽循环装入，并不是同时占据 704 个硬件槽。
768 是本版本软件策略，不代表已经证明设备有 3 MiB 可用程序空间。

电脑端的保守包预算为 3,000,000 字节，计入镜像、profile、metadata 和默认 8 KiB
余量；计算器还检查当前真实剩余存储。加载器本身、其他程序及文件系统开销都需要空间。
SH4 的 `0x042E` 可能写入 64 位结果，因此必须给两个字的缓冲区并识别输出宽度，
不能只传一个 int。依据是[原研究作者的 SH4 兼容性说明](https://www.casiopeia.net/forum/viewtopic.php?f=11&t=1754)。
页表限制、存储不足、常驻 RAM 不足、目标堆预检失败分别拒绝并显示错误码。
目标堆预检只反映当时能否分配，后续分配仍由接入方负责检查。

末页仍以 4 KiB 粒度映射。拒绝超出文件的缺页请求，不等于末页已经装入后可以提供逐字节
边界保护。不能把页表容量余量理解为允许读取文件末尾之外的任意内容。

## Profile 格式与接入

`EXT.PRF` 固定 128 字节，大端。0 为 `FXEXT002`，8 为版本 2；12 镜像字节数；
16 起址 `0x00300000`；20 入口 `0x00300200`；24 有效页数；28 容量；32 运行时
ABI=1；36 flags=1；40 最低剩余存储；44 目标堆预检字节数（0 表示目标自行负责）；
48–79 完整 SHA-256；80 二进制 hook 数量必须为 0；84–127 保留为 0。

CMake 使用 `add_subdirectory(...)` 和 `FxStudio::LargeRuntime`，C/C++ 头文件为
`<fxlarge/runtime.h>`。`FxLargeApi` 保留 Giac 已有的 28 字节 MapApi v1，加载器作为
入口第三个参数传入。`fxlarge_bind()` 必须在硬件检测和系统调用前执行，并在目标清理
`.data/.bss` 后再次执行；两个函数指针槽必须位于常驻 URAM。

仅链接库不等于已经适配。接入方还必须完成：

1. 将 TLB 异常处理放在常驻 RAM，保存正确的寄存器组、PR、GBR、MACH/MACL，调用
   `fxlarge_refill_slot`；失败时进入原通用异常处理器，成功时恢复并 `rte`。
2. 系统调用经过 `fxlarge_syscall_slot` 的汇编网关；它不是普通 C 函数调用约定。
3. VBR 世界切换使用 `fxlarge_atomic_mask()`；目标 VBR 和驱动完整安装之后才用
   `fxlarge_resume_interrupts()` 恢复中断掩码。
4. 退出前停止目标定时器、销毁运行时并恢复 shim VBR，之后才能返回。
   `fxlarge_unbind()` 会验证 VBR 所有权；它不会假装能修复任意半初始化状态。

现有 `payload-adapter/` 保留 Giac 的实际启动、异常、系统调用、切换和构造/析构适配。
普通未修改 gint 不能只链接这个库就运行。首版仍禁止执行期间外部 Bfile 操作、异步 OS
回调及直接重启/关机，确保真实 Flash 页地址不被目标自行搬移。MENU/OFF 要求目标先
完成析构再交给加载器。本库不承诺保留任意调用者的栈，也不提供嵌套调用恢复。

源码接入完成后，使用 `tooling.ext_profile.wrap_raw()` 生成 512 字节头：前 16 字节为
无 NUL 的 `FXLARGE-PAYLOAD1`，之后五个大端字为 `(1,0x00300200,raw_bytes,1,1)`，
其余至 511 为零。这个头只是 ABI 声明，不能作为自动分析正确或实机兼容的证明。
电脑工具按旧版本精确 hash 识别既有 Giac；新加载器没有写死其 hash。

## Hook 与 Ghidra 的实际边界

替换异常处理、入口分发表在技术上可行，但必须覆盖 VBR 所有权、常驻入口、寄存器与
延迟槽、原处理器链、所有世界切换，以及失败时恢复顺序。Ghidra 找到引用或反编译成功
本身不证明这些条件全部成立。

`tooling/hook_review.py` 已提供独立证据验证：绑定镜像 SHA、精确指令字节、文件偏移
与虚拟地址、延迟槽确认和异常所有权字段。结果始终注明 `runnable:false`；EXT v2
不执行任意二进制 hook 补丁。未知无源码程序明确拒绝，不能将“生成了 profile”说成
“所有 G1A 已自动兼容”。

## 构建与核验

FxStudio 将选中的项目复制到离线编译目录，所以样例中保留小型 `vendor/fxlarge`
快照。修改库后运行 `python tooling/sync_sample_library.py`；测试命令为
`python -m unittest discover -s tests -v`，覆盖页边界、容量/存储分离、错误 profile、
hook 字节不匹配及快照一致性。用 FxStudio 打开 `probes/extended-cas`，先 Debug
再 Release；常驻段重定位检查会拒绝跳出所复制代码的引用。

错误码：10–14 为镜像打开、大小、地址查询、关闭、hash；20–23 为 RAM/重定位；
31 为 TLB 槽不足；40 为目标初始化阶段失败；51–54 为 profile/页数/包预算/hook；
55 为存储余量查询失败或不足；56 为目标堆预检失败；57 为运行时头错误；101 以上为
OS 指纹不符合。部分异常仍采取停止执行，需 RESET，不承诺恢复半初始化目标。

旧 RC1/RC2 和用户实机记录仍保留；本轮动态容量和目录选择需要重新实测，不能沿用旧版
成功结果冒充新版已经验证。

原版 KhiCAS 继续使用独立 `KLoad.g1a` 和已审核的 arena 补丁。新增目录支持要求
`IMAGE.BIN`、`KHICAS.KPF`、以 `FXKLOAD1` 开头的 4096 字节预分配 `KLOAD.TXT`；
`KLoad.g1a` 放根目录。旧根目录布局仍兼容，没有把 KhiCAS 偷换为普通映射路径。
其 MENU 状态恢复仍未获得完整实机验证。
